# Extension profile: `x_review_*`

**What it is.** Two marks several tools read the same way: an element written as **proposed** (an AI seat's write in a world whose charter says its writes land for review; a person's suggestion) and an element **checked** (someone confirmed it is still true, when, against what). Proposed is about whether an element is settled; checked is about whether a settled element has rotted. Both are read by an editor's ink (Atlas), a world doctor, a parlor (a Proposed chip on a work item an agent wrote under review) and the folder lint, which is why they are a profile with a reserved prefix and not two loose keys a person could type.

**Key names.** Profile `review`, two fields: `x_review_proposed`, `x_review_checked`. The grammar is `x_<profile>_<field>`; the prefix `x_review_` is reserved.

**On which element.** Any element. Both sit in the element's body as extension fields (so they travel in every export and share the extension cap), never in `world.json`.

**The values.**

| Key | Meaning |
|---|---|
| `x_review_proposed` | `{"by": "<the writer's own word for who made the mark: see Who by names>", "evidence": "<ids or text>", "expires": "YYYY-MM-DD"}` on a NEW element written as proposed: the writer's word for who proposed it, what it rests on, and the day it lapses if nobody acts. **Absent or `null` means settled.** A keeper named by the world's charter accepts the element by writing `null` (a clear is written, never only omitted, so a push carries it) or declines it by deleting the element. A proposed CHANGE to an existing element is never this key: it is a record beside the element (the platform's), so the settled text is never rewritten by a proposal. On onlyworlds.com a keeper accepts or declines through the API's routes (`POST /api/v2/{type}/{id}/proposals/{pid}/accept` and `.../decline` on a proposed change, `POST /api/v2/{type}/{id}/review` on a marked new element) or a package's call for them; no page and no tool has the buttons yet. |
| `x_review_checked` | `{"by": "<the writer's own word for who made the mark: see Who by names>", "at": "YYYY-MM-DD", "against": "<an id, a path or a sentence>"}`: the writer's word for who last confirmed the element still true, when, and against what (a source element, a file, a sentence naming the check). Overwritten by each later check; a world keeps no history of checks in this key. |

**Who `by` names.** `by` is the writer's own word for who made the mark, and it stays that: a claim. Nothing in a mark shows it is true, it has no format a reader may rely on, and it is never proof of who wrote the mark or the element.

A writer writes the id its platform gives it for itself, spelled as the platform gives it; where the platform names the writer by a word and not an id, that word. In a world folder linked to no platform it writes the id of its own Character, or a plain name for itself where it has none.

A reader reads `by` as stored, never trimmed: a `by` that is not a string, or is White_Space alone, names nobody; White_Space around a word or an id makes it neither. A reader always shows a `by` as the mark's word (for example "the mark names Ada"), in a form that keeps the name visibly the mark's, never as a fact of its own ("proposed by Ada", "checked by Ada"), whoever it names and whatever else agrees with it. It may put a name in the value's place in two cases only. One: its platform resolves the value to the world's owner where it is the word `owner` exactly, in lowercase with nothing around it, and to a member on its roster of that world by comparing the two as ids, by this mark's own reading and not the address profile's "The same id": a value is read as an id when the whole of it, with nothing before it or after it, is `H`, or `H` between `{` and `}`, or `H` after `urn:uuid:` (those nine characters as printed, in lowercase), where `H` is `[0-9A-Fa-f]{8}-[0-9A-Fa-f]{4}-[0-9A-Fa-f]{4}-[0-9A-Fa-f]{4}-[0-9A-Fa-f]{12}` or `[0-9A-Fa-f]{32}`; two such values name the same id when their 32 digits are the same, a letter in either case being the same digit; the name is the one the platform serves this reader, the id itself where it serves none, and the reader says beside it that this is the owner, an AI's seat or a player's seat when it is one. Two, otherwise: the value, read as an id by the same reading, is the id of a Character of the same world that this reader is served; the reader says it as that Character, with its type ("the Character Rachmaninov"), never as the member who plays it and never with a member's kind. Every other `by` is shown only as the mark's raw value: apart from any sentence that says who made the mark, never where a name stands, never with a kind beside it. A reader that says who wrote an element, or who wrote a mark, takes that from what its platform recorded of it, never from `by`, and says nothing where the platform recorded nothing.

**How a reader uses it.**
1. **A marked element is not canon until a keeper settles it.** An element whose `x_review_proposed` is an object is proposed; an element without the key, or with `null`, is settled. The mark is read by presence as the room profile (`room.md`) and the charter profile (`charter.md`) define it ("A mark counts when its value is not null: a string counts only when something is left after trimming it (the White_Space set the room profile defines), any other value (a number, an object) counts as present, and the value is never compared."), and for this mark an empty list or an empty object is absent too, since a compact reader leaves both out: an empty mark is settled, never a doubt (rule 4), and keel refuses a write whose mark is empty (`""`, white space only, `[]`, `{}`) with `422 review_mark_empty`. Readers come in two kinds, and the rule binds both:
   - **A reader that hands a world on** (a Markdown or context pack, a draught of what a Character knows, an MCP server's lists and searches, a context packet for an AI) **leaves proposed elements out unless asked for**, says in its opening line or its reply how many it left out, and labels each one it keeps **"proposed, not yet reviewed"**, with the mark still on it. It never hands a proposed element on as a fact without the label. The reason is a planted instruction: a seat whose write lands for review must not reach the next AI as canon before a keeper has read it.
   - **A reader that shows a world to its people** (an editor, a viewer, the world page, a review queue) **shows proposed elements with the mark visible**, apart from settled ones (a word before the colour, never merged into counts of what the world holds as true), since the keeper has to see them to settle them. An element asked for by its own id is served whole, mark on, to any reader.
2. `expires` past: the proposal lapsed; a reader shows it as lapsed and a doctor reports it; nothing deletes it on its own.
3. `x_review_checked.at` is the element's freshness date where it exists; last checked outranks last edited. A reader that shows age shows the check's date first and the edit's beside it.
4. A value that counts as present (rule 1) and is not an object, that is a string with something in it, a number, a list with something in it or a boolean, is never repaired and is reported by a lint; an empty value is no such value, it is settled (rule 1). A reader that hands a world on treats it as a doubt: left out unless asked for and counted with the proposed, so a doubt never reaches an AI as canon. A reader that shows a world to its people ignores it, showing the element as settled with the lint's finding beside it. The queue and the review route read an object only.
5. An object that holds at least one key is a mark, whatever its keys and whatever their values: one that lacks a key the table names, holds only keys it does not name (`{"note": "x"}`), or holds a key whose value is null (`{"by": null}`), is proposed under `x_review_proposed` and checked under `x_review_checked`, never a doubt and never settled. The lint reports each missing key; nothing repairs it; a reader shows what is there: no `by`, no proposer or checker named; no `expires`, the proposal never lapses, since rule 2 has no date to pass; no `at`, the check gives no freshness date (rule 3). A proposed one is listed by the queue and settled by the review route like any other: a keeper can only settle what the queue shows, and a mark shown as settled could never be cleared through it. This rule binds the reader, never the writer: a writer still owes every key the table names, as the writer's rules below say of a check ("a check with nothing it was checked against is not a check").

**What a writer must do.**
- Write a proposal only where the world's charter says writes of this kind land as proposed; a settled world's writer never adds the key.
- Clear a proposal with `null`, as a write of the field; never remove it silently from a local copy.
- Write a check with the real date and a real `against`; a check with nothing it was checked against is not a check.
- Keep both byte for byte when they are not yours to change, like every extension field; a re-key never enters them (§3.3 of the folder format).
- Reserve the prefix. A tool that lets people add their own fields reserves `x_review_` and shows both read-only, like `x_identity_` and `x_packet_`; a check is written through its own control (a tap on a card), a proposal only by a writer acting under the charter.

**What it is not.** Permissions (who may accept is the charter's and the platform's, not the key's), a version history (a proposed change to settled text is a record beside the element), or a stale-after rule (the check records a date; the world's own policy says how old is too old). Who may write which `by` is the platform's, like who may accept.

**Example**, in Hyperion: an AI seat proposes a new Location; a keeper later confirms a Title against its charter.

```json
{ "name": "The Lower Quays", "x_review_proposed": {"by": "0d4e8a2c-…", "evidence": "the Harbour Ledger, entry 14", "expires": "2026-11-21"} }
{ "name": "Harbourmaster",   "x_review_checked":  {"by": "2ba21540-…", "at": "2026-10-22", "against": "019a2c7e-5b31-…"} }
```

Readers today: keel writes the mark on an agent seat's new element under the world's switch, lists marked elements in the review queue and settles them through the review route; keel's draught and MCP reads leave them out unless asked; the world doctor counts them apart (the `onlyworlds` Python package, flag 12), and its Markdown pack leaves them out unless asked (`--proposed`); the parlor shows a Proposed chip on a work item an agent wrote under review, and nothing else (it has no review queue); Atlas shows a proposed element with the mark visible, counts it apart from what the world holds, leaves it out of a share page, and follows its own proposals to their end (accepted, declined with the keeper's reason, lapsed or withdrawn), and it accepts and declines nothing. Still to come, each named here as it ships: keel's checked-against card. On onlyworlds.com a writer reads its own id from `GET /me` (`membership`, lower case with hyphens); the world's owner has none there and writes the exact word `owner`, which keel reads in lower case with nothing around it. keel checks a review mark as it would be stored, which is after its own mark on an AI seat's new element under the world's switch (that mark takes the place of any `x_review_proposed` the write carried and keeps only its `evidence`, when that is a string that is not empty). From a contributor or a guest (a person's key or a seat's) it refuses, with `403 review_by_another`, a mark whose `by` holds something (as rule 1 reads a mark; a value that is not a string included) unless that `by` is the writer's own membership id or the mark is the same JSON value the element already holds. It holds the owner and a co-builder to no `by`. keel records who wrote an element (`created_by`, `changed_by`), never who wrote a mark: the review queue's `by` is the mark's own. keel's element pages and Recent changes say a `by` as the mark's word.
