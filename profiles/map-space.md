# Convention profile: map space


**What it is.** How a reader turns the standard's four map-space types into geometry: a Map's frame, a Zone's outline from its Markers, a Pin's point. The standard already says every part of it in its field descriptions (coordinates from the bottom left, `order` for the sequence, `shape` for how markers join, `depth` for z); two readers (the Unity package's C#, the Shell's `model.js`) carry the same rules with no page to replay against, and an engine would be the third copy. This page states the rules once, with a fixture. The geometry adds nothing to the world: no field, no mark, nothing stored. Two marks are a layout tool's, and rules 8 to 10 say how every tool reads them: `x_layout` on a Map (the Map is a drawing of its elements, and how it was drawn) and `x_hand` on a Pin (placed by hand); a second, small reading answers them for one Map. Rule 11 says what a tool that picks a Map, or measures or places by one, does with a layout map, and rule 12 when a writer marks one. Looks, cameras, lifts, doors, walls and rooms are a drawing tool's and are not here.

**The reading.** `mapSpace(elements)`, one reader in the SDK and the Python package (`map_space`), from the fixture beside this page. `elements` are the elements as the reader is served them (the folder's rows, or the API's), so visibility is already applied: a hidden Zone and its Markers are not in a member's or a visitor's input, and this page never brings them back. The answer is `{maps, zones, pins, out}`, in that order, every key always present. Everything is keyed by id and holds integers in the Map's pixels; a tool converts to its own units from the scale this page reports.

**The rules.**
1. **Coordinates.** `x` and `y` count from the bottom left of the Map, in the Map's pixels; `z` is in the same pixels, upward, and the Map's `depth` is the z extent. `z` is a point's elevation, never a height: a Marker at z 300 sits 300 pixels up, and a zone's height, where a tool wants one, is the tool's own key (the first folder read against this page had written a room's height into every Marker's z, and its reader read it back as wall height; both moved the same day). All are whole numbers as the standard says. A missing `x` or `y` on a Marker or Pin, or one that is not a whole number, leaves that row out, counted `no_point`; a `z` that is missing or not a whole number reads as 0. A reader holds a whole number within the range it holds exactly and reads a value past it as not whole: a value a parse had to round is not whole, so a reader whose JSON numbers are doubles holds whole numbers to 2^53 and reads past it as not whole; the fixture keeps every number within 2^53, so every reader answers alike. A `z` past the Map's `depth` is kept as written and never clipped: the reader reports, it does not fix (the Map entry carries `z_max`, the largest z among its points, beside `depth`, so a tool sees the overrun).
2. **Maps.** One entry per Map the reader is served: `{id, width, height, depth, z_max, scale, location, parent_map}`. A Map without `width` or `height` reports the extent of its own placed Markers and Pins (the largest x and y among those with a whole x and y that name the Map; a dangling or unplaced point measures nothing) in that slot, with `extent: "points"` beside it, so a drawing tool knows the frame was measured, not authored.
3. **Scale.** `scale` is metres per pixel: the Map's `x_metres_per_pixel` when it carries one (a decimal; the convention this page reads, as the lens profile read `x_lens`, until a scale field reaches the standard by motion), else `null`; a number passed through as given, with no byte guarantee across languages (a `1.0` prints as `1` in one and `1.0` in another; its decimals never had one). The World's `length_unit` is not a map scale and this page does not read it as one. A tool with no scale draws in pixels.
4. **A Zone's outline.** The Markers whose `zone` names the Zone and whose `map` names one Map, in `order` ascending, ties and missing `order` by id in code point order (an `order` that is not a whole number reads as missing). Id order is the one answer a folder and a server give alike; it is the making order only when ids are uuidv7, and this page does not claim it otherwise; one outline per Map the Zone has Markers on, as `{zone, map, shape, points}` with each point `[x, y, z]`. A repeated point is kept as written. `shape` is the Zone's own `shape` when it is `polygon` or `line`; empty, absent or any other value reads as `polygon`, as the field's description says. A Zone with no placed Marker has no outline and is counted `no_markers`, each of its unplaced Markers under its own reason; a Marker whose `zone` or `map` is not served is counted `dangling`.
5. **A Pin's point.** One entry per Pin whose `map` is served: `{pin, map, element_type, element_id, x, y, z}`. The element is the generic link as the wire serves it and a folder writes it, `element_type` and `element_id`; a Pin with neither, or with only one of the two, is still a point (a place with a name and nothing it stands for), with both null. A Pin whose element is not served keeps its ids: the reader may know the id without the row.
6. **Out.** `out` counts what the reading left aside by reason: `no_point`, `no_markers`, `dangling`, `no_map`. A reason with nothing counted is absent.
7. **A stable order.** `maps`, `zones` and `pins` by id in code point order (outlines by zone id, then map id); the same input gives the same answer, byte for byte.
8. **A layout map.** A Map whose `x_layout` is an object with a non-empty string `method` is a layout map: its Pins are a drawing of its elements, laid out by that method, or by hand when `method` is `"hand"` (a board). The mark is this key alone, never the supertype or a missing picture; `x_layout` absent, null, not an object, or without a non-empty string `method` is no layout. One key is the mark and the recipe, as `x_lens` is for a lens. The method word `hand` is this page's; any other method string is the tool's own until that method has a page (`trail-by-place` is the first in use), and a reader that does not know one reads the Map as a layout map all the same. A tool that cannot run the method draws the Pins where they are and never re-lays them; the elements the method would place without a stored Pin it leaves undrawn and says how many. It never draws a different picture.
9. **The ground.** `x_layout.settings.ground`, `{map, width, height}`, names the Map the layout stands on: `map` is its element id in the same world. A tool that draws a ground draws that Map's picture under the Pins. When the ground Map is served, its own `width` and `height` win over the recipe's; when it is not, there is no ground, and the layout is drawn on nothing. A ground with no `map` is no ground, and so is a ground whose `map` is the layout Map itself.
10. **A hand Pin.** On a layout map, a Pin with `x_hand: true` was placed by hand: a method that lays the map out again keeps it where it is and lays the rest around it. Only `true` is the mark; absent, `false` or any other value (`"true"`, `1`) reads as placed by the method. On a board every Pin is placed by hand, marked or not: nothing lays a board out again. A writer that places or moves a Pin by hand on a layout map sets the mark (a drag, a place at a tap); on a Map that is not a layout map it writes nothing, since every Pin there is placed by hand already. A method never sets it. Removing it hands the Pin back to the method's next lay-out. A writer that gives a Map with Pins a method other than `hand` marks every Pin on it `x_hand: true` first, then writes `x_layout`, or refuses: an act cut short leaves marks a plain map ignores, never unmarked Pins under a method. The order binds a Map that held Pins before the method, not a Map written new in one act with its method (a folder writer may write its Pins before its `x_layout`). On a Pin of a Map that is not a layout map, `x_hand` means nothing: a reader ignores it, and a writer need not clear it, so a Map whose `x_layout` is removed reads plain with its marks still on.
11. **Picking a Map.** Which Map stands for the world's space when a world has several stays the tool's (below). One thing is ruled: a layout map is no candidate. A tool that picks a Map for the world's space, by whatever rule of its own (no `parent_map`, the most Pins, a picture, a name, the order read), reads each Map's layout first (rule 8) and leaves out every Map that is a layout map. And a Pin on a layout map says where its element stands in that drawing, drawn over a ground or not (rule 9), and a Marker there where its Zone's outline runs in it, never where either is in the world: a tool that measures between elements or places an element in the world reads no Pin and no Marker of a layout map. A world whose every Map is a layout map has no Map for its space, and a tool says so; a tool that shows layout maps still opens one as what it is. The map-space reading and the layout reading answer a layout map as before, its Pins and its Markers with it; this rule is on the tool that picks or places from them.
12. **Who writes the mark.** The writer that knows what the Map is. A tool that lays Pins out by a method writes `x_layout` with that method; a tool that imports a surface its source holds as a board (cards placed by hand on no map of a place) writes `{"method": "hand"}`; a tool that makes a Map a person names, for whatever they mean by it, writes nothing, and may offer the person a control that says "this is a board". The test is what the Map is, never the source's word for it: an importer that meets a board holding a map of a real place marks nothing, and that Map is a plain Map (a ground when a layout names it). A method that places every Pin where its element is in the world and names no ground makes a place, not a drawing, and writes no mark: the Map is the world's space, whatever placed its Pins, and nothing on the standard's side lays it out again (the tool keeps its own recipe in its own namespace).

**The layout reading.** `layoutOf(map, maps, pins)`, one reader in the SDK and the Python package (`layout_of`), from the fixture's `layout_cases`. `map` is one Map, `maps` the Maps the reader is served, `pins` every Pin the caller holds, of any Map, as served; the reader itself keeps the Pins whose `map` names this Map's id, and reads a row as the map-space reading does (H: a row without a non-empty string id is no Pin, and a Map row without one is no Map, so the reading answers `{layout: null, ground: null, hand: []}` for it, whatever it carries; I: the last row served for an id wins). The answer is `{layout, ground, hand}`, in that order, every key always present:
- `layout`: the `method` string when the Map is a layout map (rule 8), else `null`. A method no page names answers itself.
- `ground`: when `layout` is not null, the id in `x_layout.settings.ground.map` when it names a served Map that is not this Map; else `null` (rule 9). The ground's size is not returned: the caller holds the served Map.
- `hand`: the ids of the Pins a new lay-out keeps where they are, by id in code point order (rule 7's order). On a board, every Pin of this Map; on any other layout map, the Pins whose `x_hand` is exactly `true`; on a Map that is not a layout map, `[]`, whatever its Pins carry (rule 10).

A Pin whose element the reader cannot see is still a Pin and is listed when it qualifies. A method's own `settings` are not returned or ruled here, the ground apart. The map-space reading is unchanged by rules 8 to 10: its answer carries no layout key.

**Readings ruled on the fixture** (2026-11-02): A, a Marker that is both dangling and without a point counts once, as `dangling` (served-ness before shape). B, a Marker without a whole `order` sorts after every ordered one, then by id (where the ids are uuidv7, as keel mints them, that is the order they were made in): a stated order outranks an unstated one. C, a Pin with one of its two keys reads both null. D, a missing `width` or `height` is measured from that Map's own Markers and Pins only. E, `scale` is set only when `x_metres_per_pixel` is a positive number, else null. F, `extent: "points"` appears only when a slot was measured. G, a `z` past `depth` is kept. H, a row without a non-empty string id is no element: ignored, never counted (an element is its id; what has none was never served); a link whose value is an empty string is no link, read as null, as an id that is empty is no id. I, two rows of one type with one id: the last row served wins, for every type (a reader holds one row per id). J, reading A reaches Pins: a Pin with neither a served map nor a point counts once, as `no_map`. K, `type` and `shape` are read case-exactly: `Map` is no Map and `Line` is a polygon, as the field's own sentence says lowercase. And a whole number is a JSON number with no fractional part, whatever its spelling: `2.0` reads as 2, `1.5` and `"2"` do not read; a reader in a language that keeps the spelling converts, never refuses, on the value.

**What stays the tool's**, said so nobody ports it as a rule: which Map stands for the world's space when a world has several, among those rule 11 leaves; a default scale when none is given (the C# takes 0.05); hull, area and room roles read from `role` or `x_` keys; doors as Objects with Pins, their widths and wall snaps; a lift factor on z; cameras and looks; how a layout method places, and its own `settings`; what a layout method does with a layout map's Markers. A reader that wants those builds them on this page's answer.

**The fixture** `map-space.fixture.json`: each case is the elements as one reader is served them, and a `want` that holds the whole answer, keys in order. The cases cover: `order` then id, and a Zone with no `order` at all; a repeated corner kept; `polygon`, `line`, absent and a stray value for `shape`; a Zone with Markers on two Maps; a Marker whose `zone` is not served, and one whose `map` is not; a Pin with no element, and one whose element is not served; `z` present and absent, and a `z` past the Map's `depth`; a Marker whose `x` is not a whole number; an `order` of `"2"` and of `1.5`; a Pin with one of its two keys; a Map without `width`; a Map with `x_metres_per_pixel` and one without; a hidden Zone, read as the owner and as a visitor (the visitor's input lacks it, the answer has no outline for it, and nothing in `out` names it); ids above U+FFFF for the code point order; a layout map with a Zone's Markers and a Pin on it, beside a plain Map with a Pin, read as any Map (rule 11); an empty string as a link: a Pin's `map`, a Marker's `zone`, a Map's `parent_map` and `location`, and a Pin's `element_type` and `element_id` together. Its `layout_cases`, beside `cases`, are the layout reading's: each case is the elements as one reader is served them and `map`, the id of the Map read (the reader's `map` is that row, `maps` the case's Map rows, `pins` its Pin rows; a case that reads a Map row with no non-empty string id cannot name it, so it has `map_index` instead, a list of positions in `elements`, and the answer is the case's `want` for each row read), with a `want` that holds the whole answer, keys in order. They cover: `x_layout` absent, null, a string, an object without `method` but with a ground, `method` `""`, and a `method` that is not a string; a board with two unmarked Pins and one marked; a known method with `x_hand` as `true`, `"true"`, `1`, `false` and absent; a marked Pin served with its element link null; a method no page names; a ground naming a served Map, a Map not served, no `map`, a `map` that is an empty string, and the layout Map itself; a plain Map whose Pins keep their marks after `x_layout` is removed; a Map with three Pins that gains a method, as the writer leaves it; Pins held out of id order, and a Pin on another Map; two Pin ids that a UTF-16 comparison and a code point comparison put in different orders; a Pin id repeated, marked in its first row and not its last, and the reverse; a Pin row with no `id`, one whose `id` is a number, and one whose `id` is an empty string; a Map row with no `id`, and one whose `id` is a number, each carrying a method, a served ground and marked Pins, one of them with no `map`; a Map row whose `id` is an empty string, a board with a Pin whose `map` is an empty string too; a layout Map and its ground, neither with a `parent_map`, the layout holding three Pins and the ground one, each read in turn (a missing parent and a Pin count neither make nor unmake a layout); a Map whose Pins a method drew, marked with that method; a Map with no `x_layout` whose Pins a tool placed at their true positions by a recipe in its own namespace; and a board of a real place, imported with supertype `Board` and no mark.

**Where it shows.** Any tool that draws a world's maps: Atlas's map view, the Shell's Deck, the Unity package, the visuals engine. Keel draws nothing with it today.
